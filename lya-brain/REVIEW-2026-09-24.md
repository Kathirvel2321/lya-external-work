**Scope reviewed:** 13 brain docs, 3 ADRs read in full + 18 more by register, 7 contracts,

## Part 1 — What is genuinely new and genuinely good

### 1. `09-LOCAL-STACK-CPU.md` is the most valuable document in the folder

Because it **changed a decision based on a measurement**. The old plan said "keep Ollama as
the offline guarantee". The new doc ran `ollama list`, got
`Error: could not locate ollama app`, and wrote:

> *"`03-MODEL-STRATEGY.md` M-5 ... and the `README` claim of an offline path are **currently
> false on this machine**. Either repair the Ollama install or stop claiming an offline tier."*

That is the single most valuable sentence in the entire folder. Documentation that **retracts
its own earlier claim when hardware disagrees** is the thing that makes a project trustworthy.
Most spec-writing goes the other way — the claim survives because nobody re-tested it.

I verified the hardware numbers independently and they are exact:

| Claim in `09` | My measurement | Match |
|---|---|---|
| Intel i3-1315U | Intel(R) Core(TM) i3-1315U | ✅ |
| RAM 7.71 GB usable | 7.71 GB | ✅ |
| 210.6 GB free on C: | 210.6 GB | ✅ |
| Windows 11 Home Single Language | same | ✅ |
| Account is **not** admin | `False` | ✅ |
| `HypervisorPresent = True` | `True` | ✅ |

**Not one number was inflated.** That is rare and it matters.

### 2. `11` §0 — refusing "unhackable" while still answering the actual need

The owner asked for "no one can hack it". The doc does not say "yes" (dishonest) and does not
say "no" (unhelpful). It says:

> **COMPROMISE ≠ DISCLOSURE.** An attacker who fully owns the laptop must still be unable to
> read your top-tier secrets, because the key that opens them is not on the laptop.

That reframing is correct engineering *and* it directly answers the owner's fear. The explicit
non-guarantee list (live-session capture, coercion, zero-days, supply chain, owner error) is
what makes the rest credible — a threat model that claims to defend everything defends nothing.

### 3. `W-2` — the finding I missed, and it is serious

> `security/auth_wall.py:88-102` uploads audio containing your **spoken security word** to
> Groq Whisper for transcription.

This is a **real** bug and I did not find it in my own pass over the code. The vault's own
second factor leaves the device. It undermines the thing it is supposed to strengthen. I read
`auth_wall.py` and the finding holds.

**It is also correctly ranked**: the doc says fix it *before* entrusting the vault with
anything real, and points out the fix is small (check the phrase locally, or match a *hash* of
the phrase rather than the transcript). Right finding, right priority, right remedy.

### 4. `13` §6 — recommending deletion of your own offensive toolkit

An AI proposing that its own capabilities be removed is unusual and it is correct here.
`skills/hacker.py`, `kali.py`, `learnhack.py` add **zero defensive value**, give malware a
ready-made recon toolkit, and create legal exposure where *you* are the suspect. The
distinction it draws — **knowledge ≠ capability**, keep the text in the vault, remove the code
from the import path — is exactly right.

### 5. `lya-platform` — the best architectural idea in the project

> Your laptop holds the crown jewels and stays boring. The risky work happens in a workshop
> that contains nothing you would miss.

Zone A / B / C with a narrow audited bridge, where **row B is designed to be thrown away**, is
the correct answer to blast radius. And the two corrections inside it are sharp:

- **"WSL2 is a work environment, not a security boundary"** — with the honest note that a
  sandbox with `/mnt/c` mounted is not a sandbox, it is a second door.
- **"The fanless VivoBook is the best test rig and the worst server"** — thermally correct, and
  it is the kind of advice that saves hardware rather than sounding clever.

The `ls /mnt/c/Users` **must fail** acceptance test is the right way to make an isolation claim
falsifiable instead of a story.

### 6. `04-BUY-A-TICKET.md` — the best-reasoned refusal in the folder

It refuses the payment step without refusing the request. Four documented walls (PSD2 SCA,
CAPTCHA, PCI scope, BOTS Act), then the constructive replacement — **she takes the waiting, you
take the 3 seconds of risk** — plus the *better* suggestion I would not have thought of
(virtual single-use card with a hard cap, so the instrument never lives inside LYA).

The line *"the waiting is the expensive part and the paying is the risky part"* is the correct
decomposition of the problem.

### 7. The `must_not` field in the eval sets

`golden.jsonl` and `agency.jsonl` state the **failure explicitly** — `must_not: "invent a
birthday"`, `must_not: "name or imply an attacker"`, `must_not: "report a blanket success"`.
A regression becomes a red test instead of a bad answer on a bad day. That is proper eval
design, and `a-016` (per-platform status when one of two platforms fails) is a case most
developers never write.

## Part 3 — The five problems, ranked

### 🔴 #1 — ffmpeg 8.1.2 is real, but **not on PATH** (material)

Three documents depend on this:

- `09` §2 and `lya-agency/README` — *"**ffmpeg** 8.1.2 installed"*
- `02-VIDEO-PIPELINE.md` step 3 — *"✅ **yes, offline, free**"*, the load-bearing step
- `05-CAPABILITY-REGISTRY.md` — `render_video` tier relies on it

What I actually found:

```powershell
(Get-Command ffmpeg)     → not found on PATH
& "C:\Users\ipvis\.codegpt\ffmpeg\ffmpeg.exe" -version
  → ffmpeg version 8.1.2 ... ✅ the version claim is TRUE
```

**So the version is right and the "installed" claim is right — but "installed" was read as
"available", and it is not.** It lives inside `.codegpt\ffmpeg\`, which is a **tool-local
install, not a system one**. Consequences:

- `subprocess.run(["ffmpeg", ...])` raises `FileNotFoundError`. The whole render step fails.
- If that folder is cleaned or the tool is reinstalled, **the video pipeline silently dies**.
- A capability marked ✅ on an unverified assumption — the exact failure mode
  `LYAPROJECTBRAIN.md` §0.1 warns about.

**Fix (10 minutes, do it before anyone trusts `render_video`):** either install ffmpeg
properly (`winget install Gyan.FFmpeg`) or resolve the path explicitly and **pin it in config**,
never by bare name. Then run one real render and paste the output. Until that line exists,
`render_video` is 🟡, not ✅ — and the docs should say so.

**The general lesson is worth more than the bug:** the hardware in `09` was measured by running
commands, so it is exact. ffmpeg was checked by *looking*, so it drifted. **Measure, don't
inspect** — it is the folder's own best principle, applied inconsistently.

### 🟠 #2 — Cerebras was dismissed on a soft claim

`08` §2 states flatly: *"Cerebras has **no free tier** ... remove it as a fallback."* The
sources suggest something more like **a free playground key plus specific free models**, not a
total absence ([Build with the Speed of Cerebras](https://inference-docs.cerebras.ai/introduction),
[Cerebras provider config](https://docs.cline.bot/provider-config/cerebras)).

**Why it matters beyond one provider:** this is the only place in the folder where a
*dismissal* was written with less rigour than the *acceptances*. Dismissals deserve the same
evidence standard — a wrong "no" silently removes an option forever, and nobody re-checks a
closed door. The honest wording is "free access exists via a playground key and specific free
models; sustained free use is **unverified** — check before depending on it." Same conclusion
(don't depend on it), correct reasoning.

### 🟠 #3 — The 70/30 ticket split is right, but "70 % automated" oversells

`01-ACCESS-TIERS.md` says the ticket task is **"70% automated, 30% permanently yours."**

But `04` itself documents **four** walls that block the automation, and the ToS/law wall
applies to the *watching and pre-filling* too — not only the payment. And `04`'s own follow-up
says: *"If a specific site is named, its ToS and robots/anti-bot policy must be read **before**
any watching or pre-filling is automated."*

So on an unnamed site, the honest figure is closer to **"~70 % automatable *conditional on that
site's ToS permitting it*"**. The nuance is in the document's own footnotes but the headline
number reads as unconditional. **Headline numbers get quoted; footnotes do not.** Say the
condition in the row itself.

| Where | Says | Measured | Verdict |
|---|---|---|---|
| `11` §1 | `shots/` 367 KB, `debug/` 1.9 MB | 0.43 MB, 1.65 MB | same finding, numbers moved |
| `09` §5 | `test_foundations.py` → **13/14** | 13/14 was *before* I installed numpy; it is now **14/14** | **stale — `numpy` was installed this session** |
| `10` §5 | `verification (6 stores exist as of 2026-09-24)` | ✅ exactly 6 | correct |

The `13/14` row is the interesting one: the folder recorded a state that **my work changed**,

### 🟡 #5 — `ADR-002` (plan-bound approval) is the riskiest decision in the set

I want to flag this because it is the one design choice that **weakens a guarantee while
sounding like a convenience**.

The current model approves **one action, once, consumed immediately.** `ADR-002` proposes
approving a **plan hash**, after which execution proceeds unattended, and *"any step that
deviates ... re-escalates."*

The ADR is honest about most of the risk — it names the stale-hash problem, requires
target+argument coverage, and specifies deviation re-escalation. That is good work.

**But two things need strengthening before this moves from PROPOSED:**

1. **Deviation detection is the entire security property, and it is the hardest part.** "A step
   differs from the approved plan" must be computed on something an attacker cannot manipulate.
   The plan hash is computed from the plan text, which is *model output*, which is *untrusted*.
   **If the plan is regenerated rather than replayed, a new plan can be hashed that "matches" a
   described goal while doing something else.** The fix is to execute the **stored, hashed plan
   text** — never a regenerated one — and to make the deviation check structural (tool + target
   set), not textual.
2. **The approval-fatigue argument cuts both ways.** The ADR rejects per-step approval because
   *"fatigue is what produces blind approval."* True — but a *single* approval for a *twelve-step*
   plan is exactly the artefact a person approves without reading. The middle ground: show a
   **compact diff of effects** (what will be created/changed/deleted, and how many) rather than
   a step list.

**Verdict: keep it PROPOSED, and do not let it be the thing that ships first.** It is right that
the current model does not scale to automation. It is also the change most likely to quietly
erode D-2. Note that `ADR-002`'s own open questions (does a nightly job need approving every
night?) are **unanswered**, and that answer determines whether this is safe.

## Part 4 — Different perspectives (what the folder does not examine)

### Perspective A — The 5-year view: this folder is now bigger than the app

Count what exists: **13 brain docs, 18+ ADRs, 7 contracts, 3 eval sets, 6 agency docs, 6
platform docs** — roughly **45 documents**, all PROPOSED, plus proposals for 10 (P-1…P-10), 11
(ADR-001…011), 12 (SEC-001…012) and 6 (R-1…R-3) more decisions.

Meanwhile `test_foundations.py` is the **only** thing actually verified end-to-end, and
`LYAPROJECTBRAIN.md` §1 still lists the app as not running.

**That ratio is the risk, not the quality.** This is the *opposite* failure from the one I
worried about last time — not over-engineering the code, but producing a specification surface
that no single person can ever implement or maintain. 45 proposals is not a backlog; it is a
slush pile, and the honest prediction is that most will be silently ignored, which then teaches
you that these docs do not matter.

**The fix is not to write less — it is to make acceptance brutal.** `10-CONTRACTS.md` §5 already
has the right idea

with "ADRs 001–011 either accepted or explicitly rejected — **none silently ignored**". Extend
that: set a hard date, force a **reject** for anything not implemented in the next two weeks,
and keep the rejected ones in a `REJECTED/` folder. **A decision register that only grows is
not a decision register.**

### Perspective B — An implementer on a different device

They receive: 13 docs of principles, 11 ADRs, a layer model with eight layers and ten steps,
and a definition of done with 10 checkboxes.

What they do **not** receive: **one working example of a capability end-to-end.** No
`tool_descriptor` filled in for a real command, no `memory_record` example, no golden eval case
actually passing, no `bench_latency.py` output.

The contracts are good and the `tool_descriptor.schema.json` `required` list is exactly right
(no capability without matcher + tier + test). But **schemas describe shape, not behaviour.**
An implementer can satisfy every schema and still build something the owner would not recognise.

**Cheapest high-value addition:** one **worked vertical slice** — `device_health` (read-only,
PUBLIC, `fast: true`, no network) implemented, tiered, tested, with its real output pasted, and
its eval row green. That single example would teach more than the remaining 40 documents, and
it would **prove the architecture is implementable at all**. Right now that is an assumption.

### Perspective C — The security of the security plan

`12` is strong, but its own structure contains a risk: **nine controls and twenty red tests**
is a lot of surface, and every one of them is currently ✗. A plan with 29 unimplemented security
controls does not make LYA safer — it makes the *gap* bigger while feeling smaller, because the
document reads as though the work is done.

**The strongest thing in `12` is the one the folder under-uses: the tests-as-claims rule.**
*"If a test cannot be written for a claim, the claim does not belong in the document."* Apply
that rule **backwards** to prioritisation: rank the 20 red tests by what happens if they fail,
implement **R-01, R-02, R-06, R-07, R-10** first (the five that correspond to the actual
guarantees G1/G2/G3), and mark the other 15 explicitly "not yet claimed." Then the security
posture is **5 true statements instead of 29 aspirational ones.**

### Perspective D — The owner's actual question, answered more simply

The owner asked for two things in plain language:

> *"no one can hack it, and if they do, they still cannot reach my passwords"*
> *"she must not do something that can totally boom the LYA system"*

Both are **answered correctly** — but they are buried. The answers are:

1. **Passwords survive a full hack** ⟸ `ADR-SEC-002` (a factor that is not on the laptop) +
   **fix `W-2` first**, because today the security word itself is uploaded.
2. **She cannot boom herself** ⟸ never runs elevated (already true), never modifies her own
   security core, never deletes her own recovery material, safe mode on integrity failure.

Both fit on **one page**. The 600+ pages around them are justification. For a single-owner
project the one-pager is the thing that will actually be read on the day it matters —
**`11` §0 and `13` §2 extracted into `ONE-PAGE-SECURITY.md`** would be the highest-value
document in the folder.

### Perspective E — The thing nobody wrote down: this is now a two-machine project

`09` and `lya-platform` together describe work happening on the MSI laptop, the VivoBook, an
Oracle VM, **and** an unnamed "real device" the owner keeps referring to. `10` says the real
build runs "on another device."

**No document defines which device is authoritative for the memory store.** `02-DATA-ROUTING.md`
v2 correctly killed multi-master reconciliation **on the grounds that you have one machine** —
and then `10` says the build happens elsewhere. **Those two statements are in tension.**

Before any of this is built: **name the authoritative device for the L3 memory store, in
writing.** If it is not the laptop, then the "three stores, no reconciliation" conclusion in
`02` v2 needs revisiting — which is fine, but it should be a decision, not a discovery.

## Part 5 — Verdict

**Good idea or bad idea? Clearly good, and better than my own earlier work.**

Concretely, what you have done that I did not:

1. **Measured the machine** and then *retracted a claim it disproved* (`09`) — that is the
   behaviour of a project that can be trusted.
2. **Found `W-2`**, a real security bug in the vault's own second factor that I missed.
3. **Reframed the security question** from "unhackable" to "compromise ≠ disclosure" (`11` §0),
   which is both honest and more useful.
4. **Proposed removing your own offensive capabilities** (`13` §6) — rare and correct.
5. **Invented the workshop architecture** (`lya-platform`), which is the best idea in the set.
6. **Refused the payment step** while keeping the request useful (`04`), with a better
   workaround than either of us started with.
7. **Wrote `must_not` into the evals** — the difference between a test suite and a wish list.

**Do these five things, in this order:**

| # | Action | Why first |
|---|---|---|
| **1** | Fix **`W-2`** — stop uploading the spoken security word | It breaks the vault's own second factor. Small fix |
| **2** | Make **ffmpeg** genuinely available (install or pin the path) and run one real render | Three docs rest on it and it does not currently work by name |
| **3** | Write **`ONE-PAGE-SECURITY.md`** (extract `11` §0 + `13` §2) | The only security doc that will be read on the bad day |
| **4** | Implement **one vertical slice** (`device_health`) end-to-end with real output | Proves the architecture is implementable; teaches more than 40 docs |
| **5** | **Force accept/reject on all 45 proposals**, with a deadline | A register that only grows is not a register |

**And one thing to stop doing:** adding documents. The next artefact should be a **`bench_latency.py`
output pasted into `04`**, or one green eval row — not another spec. The folder has proven it can
research; the open question is whether it can *finish*.
